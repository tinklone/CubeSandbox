01 · SNAPSHOT

快照:给运行中的 VM 拍一张"全息照片"

sb.create_snapshot() 把沙箱的内存 + 磁盘 + 设备状态持久化为 snap-xxx。 磁盘走 cubecow 的 FICLONE reflink,O(1) 完成;内存则在 VM 短暂 pause 期间落盘 —— 并且带三级增量策略:优先只写脏页(soft-dirty), 写完立刻 resume,源沙箱几乎无感。

CommitSandbox — 快照全链路
1
发起请求
SDK 调 create_snapshot(),经 CubeAPI → CubeMaster 建作业,gRPC 下发 CommitSandbox 到沙箱所在节点的 Cubelet。
2
磁盘:FICLONE 克隆 rootfs
cubecow 对运行中 rootfs 做 reflink(CommitTemplateRootfs),只复制元数据,O(1) 得到 tpl-snap-rootfs。
3
暂停 VM
cube-runtime 连上已有 VM 的 API socket,发 vm.pause。内存页在这一刻被"冻结"。
4
内存:三级增量落盘
vm.snapshot 写内存页。优先 soft-dirty(只写自上次快照的脏页)→ 退化 incremental → 兜底 full 全量。
5
设备状态落盘
hypervisor 导出 state.json(vCPU、virtio 设备)与 config.json(VM 拓扑),快照三要素齐了。
6
恢复运行 + 登记目录
vm.resume 源沙箱继续跑;Cubelet 写 catalog.json,Master 标记 snap-9f2c READY。全程停顿仅为内存落盘的一瞬。
02 · ROLLBACK

回滚:让同一个沙箱原地"时光倒流"

sb.rollback(snap_id) 把沙箱原地恢复到快照时刻:内存与文件系统完全还原, 但 sandbox_id、IP、tap、MAC 全部不变,上层连接无需重建。实现上不做临时 checkpoint, 而是直接 VmDelete 掉当前 VM 对象,再从快照 VmResumeFromSnapshot "长"回来 —— 快照本身保留,可以反复回滚。

RollbackSandbox — 原地恢复
1
发起回滚
SDK 调 rollback(snap_id),Master 建回滚作业并分配新的 rootfs 代数 gen+1,gRPC 下发 RollbackSandbox。
2
catalog 定位 + 派生新 rootfs
Cubelet 从本地 catalog.json 找到快照的物理卷,RollbackDeriveNewGen 从快照 rootfs FICLONE 出全新可写层 gen1。
3
删除当前 VM 对象
CubeShim 收到 RollbackSnapshot:断开 agent、直接 VmDelete —— 不做临时 checkpoint,省一次内存落盘 I/O。VMM 进程本身不退出。
4
从快照恢复 VM
VmResumeFromSnapshot:内存映射快照内存卷,设备状态读 state.json,磁盘指向新派生的 gen1 rootfs。
5
网络与身份原样保留
RestoreConfig 不携带 net 字段 —— tap、MAC、IP 沿用当前沙箱配置。sandbox_id 不变,SDK 里的 sb 对象继续可用。
6
继续运行,可反复回滚
重连 agent、恢复运行;旧 gen0 rootfs 异步回收。快照保留,可再次回滚,也可以继续写入后再打新快照。
03 · CLONE

克隆:一秒派生 N 个平行宇宙

sb.clone(n=N) = 临时快照 + 从快照并行创建 N 个新沙箱 + 自动删快照。 每个克隆体完整继承源沙箱 clone 时刻的内存与文件,但拥有独立的 CoW rootfs、 新的 sandbox_id / IP / MAC,之后写入互不可见。源沙箱只在打快照的一瞬被 pause,随后照常运行。

clone(n=3) — 快照驱动的 fan-out
1
发起 clone
SDK 收到 clone(n=3)。克隆没有独立的服务端 API,而是由 SDK 编排"快照 → 批量创建 → 清理"三部曲。
2
打临时快照
内部先调 create_snapshot():源沙箱瞬时 pause → 落盘内存/磁盘/状态 → resume,得到中间产物 snap-tmp。
3
并行创建 N 个新沙箱
每个克隆走 Sandbox.create(template=snap-tmp):FICLONE 出独立可写 rootfs,内存从快照卷恢复,分配全新的 id / tap / MAC / vsock。
4
继承 + 隔离
每个副本从源沙箱 clone 时刻的状态出发(文件、内存进程全在),之后的写入落在各自 CoW 层,互不可见;源沙箱全程照常运行。
5
自动清理临时快照
全部创建成功后,SDK 在 finally 里删除 snap-tmp;若任一子任务失败,已创建的克隆会被自动 kill(),不留孤儿资源。
04 · 三者关系

同一套底座,三种玩法

三个功能共享同一套底层机制:cubecow FICLONE 负责 O(1) 磁盘克隆, hypervisor 的 pause / snapshot / restore 负责内存与设备状态, Cubelet catalog 负责物理引用索引。Snapshot 是地基,Rollback 消费快照,Clone 编排快照。

维度 Snapshot 快照 Rollback 回滚 Clone 克隆
一句话 把运行状态持久化成 snap-xxx 把当前沙箱原地恢复到某个快照 临时快照 + 派生 N 个独立新沙箱
sandbox_id 不变(源沙箱继续跑) 不变(原地穿越) 新建 N 个
VM 操作 pause → snapshot → resume VmDelete → VmResumeFromSnapshot 为每个副本 restore 出新 VM
磁盘(cubecow) FICLONE 当前 rootfs → 模板卷 从快照卷派生新一代可写层(gen+1) 每副本 FICLONE 一份独立可写 rootfs
内存 soft-dirty / incremental / full 三级落盘 映射快照内存卷恢复 共享只读内存基线,运行后各自独立
网络 不涉及 tap / MAC / IP 原样沿用 每副本重新分配 IP / MAC / vsock
快照生命周期 持久,直到显式 delete_snapshot 回滚后快照保留,可反复使用 临时快照用完即删(SDK 自动)
典型场景 checkpoint、状态持久化、制模板 Agent 回退-重试循环、撤销失败一步 并行 rollout、A/B 实验、可重复评测
设计亮点速览
① reflink 一切:rootfs 和内存卷都靠 xfs FICLONE,克隆成本与数据量无关; ② 三级内存增量:优先 soft-dirty 只写脏页,兜底才全量,快照又快又省; ③ 回滚免 checkpoint:直接 VmDelete + restore,少一次内存落盘; ④ 控制面薄、节点厚:Master 只记逻辑 ID 与作业状态,物理卷引用全在 Cubelet 本地 catalog,故障域小; ⑤ 快照即模板:snap-xxx 可直接作为 Sandbox.create(template=...) 的入参,统一了快照与模板两个模型。
